# Varendo 0.1.0 performance reference review

Review date: 12 October 2026. Reference source:
`e50eda3f3b34a2957e5cd1f9f9228c32d3e4c84a`. Workload:
`33a7411e722a3cd85e6bd312d1fdf29690c51b031acd1285a632acaefd63f558`.

## Why the reference was renewed

The inherited budget was deliberately unapproved after
[ADR 014](../adr/014-planner-timing-diagnostics.md) removed the planner timing
gate. Its historical source also belongs to the retired upstream Git history,
not the independent Varendo repository. The default comparison correctly
rejected that metadata before measuring anything. That failure was not evidence
of a performance regression.

The current workload contains the approved diagnostic-only planner behavior and
Varendo package imports. Independent reconstruction of all 50 included paths
reproduced the historical and current workload digests. No workload exclusions,
comparison limits, assertions or measurement code were changed for this renewal.
The historical [0.6.3 review](0.6.3-performance-reference.md) remains intact.

## Same-source evidence

The owner-dispatched [probe run 38230522021](https://github.com/hermawan22/varendo/actions/runs/38230522021)
compared the clean reference with an independently archived copy of the same
commit. Three pairs ran in baseline/candidate, candidate/baseline,
baseline/candidate order. Both sources were installed from the frozen lockfile
and independently built. The probe reports `stable-probe-unapproved` and
`approved: false`; it does not itself grant approval.

The [raw artifact 11738476261](https://github.com/hermawan22/varendo/actions/runs/38230522021/artifacts/11738476261)
contains all twelve workload reports, six Chromium timeline traces, both source
manifests, environments and the complete comparison. The downloaded ZIP is
12,270,093 bytes and its SHA-256 matches GitHub's artifact digest:
`df2a09e5ccc37b7064ac0a7d09ac5ca0b77c0e23d4f3bd668c46f6c3dc6bafd0`.
The complete artifact is retained in protected maintainer storage beyond the
workflow's seven-day artifact retention.

Independent review checked both 1,829-file manifests against the exact Git tree
and freshly archived bytes and modes, and recomputed the 50-file workload hash.
It recalculated all six traces, 18,000 subsequent and 6,000 first reducer dispatch
durations, 180 subsequent and 60 first planner observations, and 240 raw 2D
timings. All six layout source-change flags show unchanged bytes. Geometry,
selection, interaction-network observations and both environments match the
reports. All 23 ZIP members also passed CRC verification.

| Metric                            | Baseline p95 observations (ms) | Candidate p95 observations (ms) | Baseline median | Candidate median |
| --------------------------------- | ------------------------------ | ------------------------------- | --------------: | ---------------: |
| Layout event                      | 4.646, 3.887, 4.164            | 3.954, 3.783, 3.730             |        4.164 ms |         3.783 ms |
| 2D mutation/DOM and forced layout | 43.3, 42.6, 44.2               | 45.0, 45.9, 44.5                |         43.3 ms |          45.0 ms |

Layout changes by −0.381 ms (−9.150%); 2D changes by +1.7 ms (+3.926%). Neither
exceeds both retained relative limits: **20% and 2 ms**. The baseline and
candidate are the same source; these differences show observed run variation,
not an improvement or regression between software versions.

Every subsequent reducer dispatch p95 is 0.4–0.5 ms against the retained 4 ms
limit. Every large-table sample mounts 44 rows against 100. Script, layout and
paint trace phases are present. Layout traces contain only 15–17 layout events;
nearest-rank p95 is their largest event, which limits percentile precision.

Each 2D run retains all 40 observations, the dense 1,000-row data and 250 null
values, bounded geometry, exact-data alternatives and selection continuity.
Interaction-triggered requests are zero. Its timing includes DOM updates and
synchronous layout reads; it is not paint or input-to-paint latency.

Planner p95 observations are retained as diagnostics:

| Pair | Baseline planner p95 | Candidate planner p95 |
| ---- | -------------------: | --------------------: |
| 1    |              15.6 ms |               14.1 ms |
| 2    |              15.1 ms |               15.0 ms |
| 3    |              16.0 ms |               13.5 ms |

There is no absolute planner threshold or replacement timing gate. First and
subsequent observations reuse a loaded page and are not a cold-cache benchmark.
Individual subsequent planner observations reach 29.9 ms and first reducer
dispatches reach 11.6 ms; these raw observations remain in the artifact. The
4 ms reducer p95 assertion applies to the subsequent dispatch distribution.

## Environment and scope

Both environments match the recorded immutable Playwright container
`sha256:bc6ab0d6d44ff4826e4cb8c1e6d801e185bfc42bb0753f8e2a30efc70db054c7`,
Linux x64, Node 24.20.0, pnpm 11.24.0, Playwright 1.63.0, browser executable
hashes and the 39-file font inventory. Layout uses 1280×720, en-US/UTC and scale
1; 2D uses 1440×900, de-DE/Europe-Berlin and scale 1. The measurement host was
an AMD EPYC 7763 with four logical CPUs, 16,766,414,848 bytes of memory and
kernel 6.17.0-1022-azure.

The accompanying metadata records acceptance of this exact reference after the
maintainer-requested renewal and independent evidence review. All three-pair,
relative and remaining absolute budgets are unchanged. This approval is separate
from the diagnostic probe, whose original unapproved result remains intact.

This source-bound reference does not qualify other machines, browsers or general
capacity. The clean
metadata candidate must subsequently pass the ordinary three-pair comparison
against this fixed source, as described in the
[approval procedure](paired-performance.md#bootstrap-and-approval).
Functional CI, package publication and deployment keep their separate gates.
